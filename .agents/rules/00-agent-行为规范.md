# Agent 行为规范

与项目技术规范（01~06）并行生效，冲突时以技术规范为准。

## 沟通

- 代码注释：中文
- 代码术语：保留原文
- 用户交互：中文

## 任务流程

必须严格遵守下面的流程：

### 1. 编码前先思考

不要主观臆断，不要隐瞒疑问，清晰权衡取舍方案。开始开发前：

- 明确列出各项假设，不确定就主动询问
- 存在多种理解方式时，全部罗列出来，不擅自私自选择
- 存在更简洁实现方案时主动说明，合理情况下敢于提出反对意见
- 内容存在模糊不清时立刻暂停，点明困惑点并及时沟通

### 2. 优先简洁实现

用最少代码解决问题，不做多余推测拓展：

- 不额外开发需求以外的功能
- 一次性使用的代码不做抽象封装
- 不擅自增加未要求的扩展性、可配置性
- 不对不可能出现的场景编写异常处理
- 写了 200 行发现能优化为 50 行时，务必重构简化

自我审视：资深工程师是否会认为这段代码过于复杂？如果是，就进一步简化。

### 3. 精准改动代码

只修改必要内容，只清理自身产生的冗余。修改存量代码时：

- 不擅自优化周边代码、注释、格式排版
- 不对运行正常的内容进行重构
- 贴合原有代码风格，即便有更好写法也保持统一
- 发现无关无效代码，仅备注说明，不自行删除

自身改动产生废弃内容时：

- 删除本次修改后不再使用的导入、变量、函数
- 未经要求，不删除原本就存在的无效代码

检验标准：每一行修改内容，都能直接对应用户需求。

### 4. 围绕目标落地开发

明确验收标准，反复校验直至符合要求。将任务转化为可验证目标：

- 新增校验逻辑 → 编写异常入参用例验证
- 修复问题 → 先复现、再修复、后回归确认
- 重构模块 → 重构前后行为完全一致

多步骤任务，先简要梳理执行方案，每步「执行 → 验证：核对结果」，重复直到完成。

### 5. 大段删改后先核对再验证

整段删除 / 重排代码（含按行号截断、批量替换）后：

- 先核对文件三段结构（template / script / style）完整，再编译
- 编译验证必须包含被改文件自身的产物抽查（wxss / js 是否生成、关键类名是否存在），不能只看命令退出码

（教训：结算页清理残留代码时按行号截断误删了文件尾 `<style>` 引用行，整页样式失效）

## 日志记录（强制）

执行计划、修改代码、review 代码时，必须在 `.agents/logs/` 对应目录创建记录文件：

| 场景 | 目录 |
|---|---|
| 执行计划（写计划 / 按计划推进） | `.agents/logs/plans/` |
| 修改代码（任何代码改动） | `.agents/logs/changes/` |
| review 代码（审查自己或他人的改动） | `.agents/logs/reviews/` |

**文件命名**：`YYYYMMDD-<type>-<slug>.md`，type 为 `plan` / `change` / `review`，slug 为任务关键词（小写英文短横线，如 `room-code-qr`）。同日同类型多份时加序号：`20261013-change-room-code-qr-2.md`。

**文件内容**（简短，不废话）：

```md
# <标题>

- 日期：YYYY-MM-DD
- 任务：<一句话说明做了什么/要做什么>
- 内容：<要点列表：计划步骤 / 改动文件与原因 / review 结论>
- 结果：<验证方式与结果 / 待办>
```

- 当天多次改动同一任务可追加到同一文件，不强制拆分
- 记录在动作完成时即时写入，不攒批

## 禁止

- 主动 commit（改动保留在工作区，由用户确认后自行提交）
- 未经用户同意引入新的第三方业务库
- 暴露密钥（私密 key / 密码等；注：微信 AppID 与云开发环境 ID 属公开标识符，按约定直接写死在代码里，不算密钥）
